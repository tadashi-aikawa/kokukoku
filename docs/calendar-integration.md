# カレンダー連携 仕様書

Googleカレンダーの「本日の残予定」をKOKUKOKUのパネルに表示し、開始前に通知する機能の仕様。
2026-07-18 タダシ・迅雷の要求分析および EventKit 実機検証に基づく。Codex交差レビュー1周目の指摘を反映済み。

## 背景・要求

- **R1**: 次の予定を気にせず作業に集中したい(MTGを忘れない仕組み)
- **R2**: 移動時間を考慮して動きたい(どのMTGは早めに終わらないとまずいか把握したい)
  - 達成基準: **予定間の間隔と場所を並べて見せ、判断はユーザーが行う**。移動時間の計算・推定はしない(2026-07-18 タダシ決定)
- **R3**: MTGに迷わず移動したい(物理は場所へ、オンラインはリンクへ)
  - 達成基準: **行クリックでカレンダーの予定詳細ページを開ける**(Meetへは詳細ページから入る)。物理は**場所を確認できる**まで(Maps起動はしない。2026-07-18 タダシ決定)
  - 2026-07-19 改訂(タダシ決定): 当初の「会議リンクをパネルから直接開ける」を廃止。Googleが参加者付き予定へMeetを自動追加するためオンライン印の情報価値が薄く、詳細確認への導線の方が実用的なため
- **R4(将来・潜在)**: MTG開始時の計測切替を忘れたくない(自動フォーカス構想の源泉。今回はスコープ外)

## 取得方式(決定事項)

**EventKit を採用する**(2026-07-18 タダシ承認)。

- 認証はOS委譲: システム設定 > インターネットアカウントにGoogleアカウントを追加するだけ。Cloud Console・OAuth自前実装は不要。会社環境でもRaycastのカレンダー同期実績があり、アカウント連携済みの前提が立つ
- 実機検証で確認済みの取得可否:
  - 予定名称・開始・終了・場所: そのまま取得可
  - 参加者+参加ステータス: `EKParticipant.participantStatus` で取得可(未回答=pending を実証。辞退=declined は同機構のため取得可能と判断、実招待での追検証は今後)
  - Meet URL: `url` プロパティではなく **説明文(notes)内の定型文**(`Google Meet に参加: https://meet.google.com/...`)として降りてくる。正規表現で抽出する
  - 説明文: 同一オブジェクトで取得可
- 制約(実測):
  - **変更反映は約3〜4分遅れる**。`refreshSourcesIfNecessary()` にはthrottleがあり、呼んでも即時同期は保証されない(効いた場合は数秒後に `EKEventStoreChanged` が発火)
  - **中止(削除)された予定は `status = .canceled` では残らず、黙って消える**。中止の検知はスナップショット差分で行う(後述の誤報対策あり)
- 常駐プロセスの作法(実機検証での知見): メインスレッドで RunLoop を回し `.EKEventStoreChanged` を購読しないと、外部変更後の再クエリが古い(または空の)結果を返す。Thread.sleep でのポーリングは不可

## 設定

`~/.config/kokukoku/config.toml` に `[calendar]` テーブルを追加する。**テーブルが存在しない場合、カレンダー連携は完全に無効**: EventStore の生成・権限要求・タイマー起動を一切行わない(既存ユーザーには権限ダイアログも出さない)。

```toml
[calendar]
# 対象カレンダー名(必須)。EventKitのカレンダー名(Googleカレンダー上の表示名)と一致させる
name = "一般"
# 定期更新の間隔(分)。省略時 5
refreshIntervalMinutes = 5
# 通知を出すタイミング: 予定開始の何分前か。省略時 5
notificationLeadMinutes = 5
# パネルの予定行に表示する参加者数の上限。超過分は「他◯人」に畳む。省略時 5
maxAttendees = 5
# 展開前に表示する予定数の上限。超過分は「他◯件」に畳む。省略時 3
# (パネルの本業は計測操作のため控えめの既定。2026-07-19 タダシ決定)
maxVisibleEvents = 3
# 自分自身のメールアドレス(任意)。参加者一覧から自分を除外する。
# EventKitのisCurrentUserはGoogleアカウント連携で効かないことを実測済みのため設定で指定する
selfEmail = "you@example.com"
# タイムラインのレールを表示する最小間隔(分)。これ未満は「間隔なし」の接触表現。省略時 1
gapRailMinutes = 1
```

- `name` が空文字の場合は設定エラー(既存のvalidateと同様に `ConfigError.invalid`)
- `refreshIntervalMinutes` / `notificationLeadMinutes` / `maxAttendees` / `maxVisibleEvents` / `gapRailMinutes` は 1 以上。0 以下は設定エラー
- `notificationLeadMinutes < 5` は許容するが、同期遅延(最大3〜4分)により直前変更を拾えない可能性がある旨をREADMEに注記する
- カレンダー名の解決: 一致するカレンダーが **0件** ならエラー状態(セクションに「カレンダー『◯◯』が見つからない」と表示)。**複数一致**(別アカウントに同名カレンダーがある場合など)もエラー状態とし、`ソース名/カレンダー名` の候補一覧を表示して設定の見直しを促す。統合はしない(単一カレンダーのスコープを維持)
- `Resources/Info.plist` に `NSCalendarsFullAccessUsageDescription` を追加する(権限要求の必須キー)

## データモデル(Core)

```swift
public struct CalendarEvent: Equatable, Sendable {
    public var key: EventKey       // 同期をまたぐ論理キー(下記)
    public var title: String
    public var start: Date
    public var end: Date
    public var location: String?   // 物理の場所文字列(空なら nil)
    public var meetURL: URL?       // notes から抽出した会議URL
    public var attendees: [Attendee]
    public var notes: String?      // 説明文(Meet定型文含む生テキスト)
    public var myStatus: ParticipationStatus  // 自分の参加ステータス

    public struct EventKey: Hashable, Sendable {
        public var externalIdentifier: String  // EKCalendarItem.calendarItemExternalIdentifier
        public var occurrenceDate: Date        // EKEvent.occurrenceDate(定期予定の各発生を区別する「元の」発生日時)
    }

    public struct Attendee: Equatable, Sendable {
        public var name: String?
        public var email: String?  // mailto: URLから抽出
        public var status: ParticipationStatus
    }

    public enum ParticipationStatus: Equatable, Sendable {
        case accepted, pending, tentative, declined, unknown
    }
}
```

- **論理キー**: `EKEvent.eventIdentifier` は同期・カレンダー移動で変化し得るため、差分・通知済み管理のキーに使わない。`calendarItemExternalIdentifier` + `occurrenceDate` の複合キー(`EventKey`)を用いる。`occurrenceDate` は定期予定の各発生を区別する「元の」発生日時で、**発生の時刻が変更されても変わらない**ため、時刻変更は同一キーの CHANGED として素直に照合できる(**予定の同一性はEventKey、通知の回は後述の「通知回」**で管理し、両者を分離する)
  - **実測注記(2026-07-19)**: 上記の「時刻変更でもキー不変」は**定期予定の発生にのみ**成り立つ。**単発予定では occurrenceDate が開始時刻に追随する**ため、時刻変更は CHANGED ではなく **ADDED+REMOVED** として観測される(実測: 01:00→01:30 の変更が `+1 ~0 -1`)。消えた側のキーは externalIdentifier の再照会でアイテムが見つかり「取得範囲外への移動」扱いになるため**中止の誤報にはならない**。通知済み管理も通知回=(EventKey, 開始時刻)の単位のため、新キー+新開始時刻=新しい通知回として正しく再通知対象になる(設計変更は不要)
- **Meet URL抽出**は Core の純ロジック: notes から `https://meet.google.com/xxx-xxxx-xxx` 形式のURLを正規表現で抽出する。将来Zoom等へ広げる場合もここに追加する
- **myStatus** は attendees のうち自分(isCurrentUser)のステータス。attendees が空・自分を特定できない場合は **`.unknown` とし表示対象に含める**(「辞退情報を取得できない予定は表示する」保守的フォールバック。参加者情報を提供しないカレンダーがあるため)
- ParticipationStatus のマッピング: accepted / pending / tentative / declined を対応させ、その他(delegated 等)は `.unknown`。**非表示にするのは declined のみ**(tentative・unknown は表示)

## 取得層

### スナップショットの二層構造(Core の純ロジック)

差分の誤報(P1指摘)を防ぐため、スナップショットを二層に分ける:

1. **生スナップショット**: 対象カレンダーの「今日0:00〜明日0:00に開始する予定」全件(フィルタ前)。**取得が成功した場合のみ**更新する
   - **取得成功の定義**: 権限が有効で、対象カレンダーが一意に解決できた状態でクエリできたこと(EventKitのクエリ自体は失敗を返さないため、成否はこの2状態で判定する)。**成功時は結果が0件でも正当な結果として更新する**。0件への遷移で消えた予定も他のREMOVEDと同様に下記の再照会による中止確定を経るため、全予定の正当な削除は全件中止として検知される
   - **取得失敗**(権限喪失・カレンダー未解決)の場合はスナップショットを更新せず、エラー状態に遷移する(古い内容で中止・変更を判定しない)
2. **表示用リスト**: 生スナップショットに表示フィルタを適用したもの

差分(ADDED / CHANGED / REMOVED)は**生スナップショット同士**で取る。これにより「予定が終了した」「辞退に変えた」は REMOVED にならず、中止(削除)の候補は生スナップショットからの消滅に限られる。

- **REMOVED を「中止」と確定する条件**: 生スナップショットから消えた予定は、Platform側で `calendarItems(withExternalIdentifier:)` により**再照会し、該当アイテムが存在しない場合のみ削除(中止)と確定**する。再照会でアイテムが見つかった場合は削除ではない(取得範囲外への移動・翌日への変更など)ので、CHANGED(範囲外なら表示対象から静かに外れる)として扱う
- 再照会が実行できない・結果に確証が持てないケース(取得エラー直後など)では中止と断定せず、通知文脈では「予定を確認できなくなった」と表示する
- **日付境界**: クエリ範囲(今日0:00〜明日0:00)は毎回の再クエリ時に現在日付から計算し直す。さらに**0時を跨いだことを検知したら即時に再クエリしてスナップショットを当日基準に切り替える**(定期タイマーとは別に日付変更を監視する。`EKEventStoreChanged` の発火には頼らない)

### 表示フィルタ(Core の純ロジック)

1. **終日予定は除外**
2. **自分が辞退(declined)した予定は除外**(未回答・仮承諾・不明は表示)
3. **表示対象は「今日中に開始し、終了が現在時刻より後の予定」**(進行中を含む)。日境界は `Calendar.autoupdatingCurrent`(ローカルタイムゾーン)の `startOfDay` で計算する。前日から続く進行中予定・翌日開始の予定は対象外
4. **並び順**: `start → end → 論理キー` の安定ソート(EventKitのクエリ結果に順序保証がないため)

### 同期(Platform: EventKitアダプタ)

- `[calendar]` 設定がある場合のみ、起動時に `requestFullAccessToEvents` で権限を要求。拒否された場合はパネルの予定セクションに権限エラーを表示(アプリ自体は従来機能で動作継続)
- `.EKEventStoreChanged` を購読し、発火したら再クエリしてスナップショットを更新
- `refreshIntervalMinutes` ごとに `refreshSourcesIfNecessary()` を呼ぶ(同期のキック)
- **スリープ復帰・システム時計/タイムゾーン変更時**(`NSWorkspace.didWakeNotification` 等)は即時に再クエリし、通知予約を再構築する
- パネル表示中・通知表示中はスナップショット更新を即座に描画へ反映する
- **ライフサイクル**: アダプタは `start()/stop()` を持ち、`stop()` で observer 解除・タイマー停止・通知予約破棄を行う。設定再読込(既存のコンポーネント再生成)では旧アダプタを `stop()` してから新アダプタを `start()` する(多重購読・二重通知の防止)。表示中の通知パネルは設定再読込で閉じる

## 一覧UI(パネル)

「本日の残予定」セクションを**ヘッダー(時計)の直下**に置く(2026-07-19 タダシ決定: カレンダーの予定は計測項目と独立した概念のため、「上=時間の世界(いま=時計+これから=予定)/中=計測項目/下=フッター」のゾーニングで分離する。セクション背景はヘッダーと同色でまとめる)。

- 各予定行の表示: **予定名称・開始時刻・終了時刻・場所**。開始は明色・終了は沈み色で塗り分け、パッと見で区別できるようにする(2026-07-19 タダシ指摘: `01:00-02:00` の隣接は読みにくい)。表示デザインの詳細(配色・アイコン・余白)は実装時にスクリーンショット比較で決める
- **参加者一覧**を**次の予定(先頭)だけ**2行目に表示する(2026-07-19 タダシ決定: 移動後の場所把握に必要なのは次の予定だけで、それ以外は行クリックの詳細ページで足りる。当初の全予定表示からFT前検討で変更)。名前はEventKitではメールアドレスで降りてくることが多いため、メール形式なら**ローカル部(@より前)**を表示する。**自分自身(`selfEmail`)は除外**する(純ノイズのため)。**主催者を特定できた場合は強調色で先頭に置く**(招待されたMTGのみ。自分で作った予定は organizer がカレンダー自身になるため強調なし。自分が主催者の場合も強調なし)。`maxAttendees`(既定5、主催者込み)を超えた分は「他◯人」に畳む。参加者情報が無い予定は2行目なし
- **予定間の間隔表示(R2)**: 左端のタイムラインで、**空き時間の有無をレール(縦線)の有無で表現**する(2026-07-19 タダシ発案・4人検討で再設計。分数の常時表示は廃止 — 間隔情報は例外報告であり、全件報告に価値がないため)
  - 間隔が `gapRailMinutes`(既定1分)以上: **淡色のレール**。分数は出さない
  - 間隔が閾値未満(back-to-back含む): **明るい生成り(テキストと同格のフル明度)の太めレール**で「間がない」連鎖を示す(点との余白は淡色レールと同一)。連鎖は「危険」でも「いま」でもない構造情報のため**炎色帯(金茶〜朱)を使わない** — 当初の朱は連続MTGが日常のためアラート疲れ、次の燻し橙は計測中ネオンと同色相帯で紛らわしく、いずれも却下(2026-07-19 タダシ指摘+4人検討で確定)。タイムライン内は「**繋がりの強さ=明度、色相ジャンプ=異常(朱)**」の一軸文法
  - 時間帯の重複: **朱レール**+朱の「**◯分重複**」(食い込み量は判断材料のため数字を残す)
  - **点は全予定で同色(明るい生成り)に統一**する。点=予定そのもの(ノード)、レール=関係(エッジ)であり、間隔の意味はレールだけが背負う — 点の色が予定ごとに違うと予定の種類が違うように読めるため(2026-07-19 タダシ指摘で確定。先頭の点だけ金茶にする合図も廃止 — 次の予定の合図は時計右のカウントダウンが担う)。連鎖の一体感は「明るい点+明るいレール」の連なりで表現される
  - レール長の時間比例はしない(縦の高さが予定次第で暴れて一覧性が下がるため。行は等高・レールは記号)
- **進行中(開始済みで終了前)の予定は静かに区別する**(2026-07-19 タダシ提案・3人検討で採用。議論録: owlery `shared/discussions/2026-07-19 KOKUKOKU進行中予定の強調表示検討.md`)。先頭位置は進行中/未開始の両義で状態を語らず、カウントダウンの文言差は一瞥にならないため。ただし「今」の合図は計測中ネオンが既に背負っており、強調ではなく**恒常の弱いマーカー**で示す(色相は増やさない):
  - **点のリング化**: 進行中の予定の点だけ、同色・同サイズのまま**中抜きリング**にする(塗り=これから、抜き=いま消化中。色相・サイズを変えないため予定の種類の違いには誤読されない)
  - **時刻の明暗反転**: 進行中の行だけ開始を沈み色・終了を明色にする(「**明るい時刻=次に来る境界**」の読みで未開始行と一貫。カウントダウンの判定と同型)
  - **判定は先頭行限定ではなく各行 `start <= now`**(重複時は2件目以降も進行中になり得るため。先頭だけの合図では重複ケースで嘘をつく)
  - nowライン(レールは時間比例しないため位置が嘘をつく)・行背景(通知強調・計測中ネオンと衝突)・進捗バー(「長さ=時間」の第二文法が「レールは記号」と衝突)・テキストバッジ(等高グリッド侵食+カウントダウンと二重)は不採用
- 先頭の予定: 未開始なら「あと◯分」、**進行中なら「終了まで◯分」**を**時計セクションの右端**に表示する(「いま」の情報のため時計の段に置く。予定行に置くと先頭行だけタイトル幅が縮み折り返し位置が揃わないため。2026-07-19 実装時に決定)。**色は緊急度連動**: 30分超は沈み色・30分以内は強調色・10分以内は警告色(常時同じ強度で主張させない。2026-07-19 FT前検討でタダシ決定)。**60分超は「1時間10分」の時間表記**にする
- **行クリックでカレンダーの予定詳細ページをブラウザで開く**(2026-07-19 タダシ決定。Meet印・Meetリンク直接起動は廃止し、詳細確認への導線に変更。Meetへは詳細ページから入る)。詳細URLは `eid = base64url("<eventId> <organizerEmail>")` で組み立て、組み立てに必要な情報が無い予定はその日の日ビューへフォールバックする(キーボード選択の Enter でも同様に開ける。後述の「キーボード操作」)
- 説明文(notes)はパネル一覧では表示しない(データとしては保持。表示手段は将来検討)
- **表示件数の上限は `maxVisibleEvents`(既定3)**。超過分は「他◯件」の1行に畳み、**クリックで全件展開**する。展開中は末尾の「畳む」クリックで戻し、パネルを閉じると畳んだ状態に戻る(2026-07-19 タダシ要望で上限の設定化とトグルを追加。既定はFT前検討で5→3: パネルの本業は計測操作のため、閲覧ゾーンが操作ゾーンを侵食しないよう控えめに)
- 予定が0件の場合はセクションごと非表示。カレンダー連携が無効([calendar] 未設定)の場合、パネルは従来のまま
- エラー状態(権限拒否・カレンダー名不一致・複数一致)はセクション内に表示する
- **レイアウト**: パネル高は予定セクションの行数を含めて動的に計算する(`PanelLayout` に予定セクション高を組み込み、フッター・インライン時間編集の座標も連動してオフセットする)。表示中に予定数が変わった場合はウィンドウ高を再計算し、**画面中央位置を維持したままリサイズ**する
- **キーボード操作**: 予定行・「他◯件/畳む」行を既存の j/k 選択ループに含め、「予定セクション→プロジェクト行」の一巡で回す(2026-07-19 タダシ決定。当初の「ループに含めない」を FT 前に改訂 — キーボード至上主義の運用ではマウス専用の予定行だけ文法から浮くため)
  - Enter の確定動作は選択対象で分岐: 予定行=詳細ページを開いてパネルを閉じる(クリックも同様。フォーカスがブラウザへ移るため、パネルを残してフォーカスを戻すよりホットキー再表示のほうが楽 — 2026-07-19 タダシ決定)/「他◯件」=全件展開(カーソルは展開で現れた先頭の予定へ)/「畳む」=上限表示へ戻す(カーソルは「他◯件」行に留まる)
  - 参加者・エラー・中止告知・鮮度の行は操作対象がないため選択ループに含めない
  - 数字キー(1-9)・`e`(時間編集)はプロジェクト行専用のまま
  - 選択の合図はプロジェクト行と同じ「消灯版カプセル輪郭」。予定の増減で選択中の行が消えた場合は選択を外す
  - 通知モードのパネルはフォーカス非奪取(キーボードを取らない)ため、キー操作は通常パネル限定

## 開始前通知

- 各予定の「開始 `notificationLeadMinutes` 分前」に**パネルを自動表示**し、該当予定を強調表示する。**同時刻に複数の予定が該当する場合は1枚のパネルでまとめて強調**する
- 通知パネルの挙動(通常表示との差分):
  - **フォーカスは奪わない**(作業への割込は視覚のみ。表示中も奪わない)
  - **パネル外クリックでは閉じない**。閉じる操作は**パネル上の常時表示の閉じるボタン、または既存のパネルトグルホットキー**(Escキーはフォーカスを持たないため使わない)
  - 通常のホットキー起動パネルは従来どおり外クリックで閉じる
- **表示内容は「取得済みの最新データ」**であり、リアルタイム保証はしない(同期遅延3〜4分の制約)。通知パネルには**最終取得時刻**(アプリがEventKitから最後に取得成功した時刻。Googleとの同期完了時刻は把握できないため、それより新しく見せない)を「◯分前時点の情報」の形で表示し、直前の変更が未反映の可能性を利用者が判断できるようにする。**取得から5分未満の新鮮なうちは表示しない**(常時表示だと視線が慣れて肝心のときに読まれないため。2026-07-19 FT前検討でタダシ決定)。表示の60秒前と表示時点に `refreshSourcesIfNecessary()` をキックして鮮度を上げる努力はする
- 表示中も `EKEventStoreChanged` による更新を反映し続ける:
  - **中止の明示**: 通知予約済み(または表示中)の予定が生スナップショットから消滅した場合、「この予定は中止になった」旨を表示する(黙って取り消さない)。確証がない場合(取得エラー等)は「予定を確認できなくなった」と表示する
  - **変更の追従**: 開始時刻が変わった場合は通知予約を再計算する。表示中に内容が変わった場合は新しい内容で再描画し、変わった旨を示す
- **通知済み管理と catch-up**(Core の純ロジックとしてテスト可能にする):
  - **通知回の定義**: 通知済み管理は「予定の同一性(EventKey)」ではなく **通知回 = (EventKey, 開始時刻)** の単位で行う。同じ通知回への通知は1回まで
    - **後ろ倒し**(開始時刻が変わった): 開始時刻が変わると新しい通知回になるため、新しい通知時刻で再度通知対象になる
    - **前倒し**(開始が近づいた): 新しい通知回の通知時刻が既に過ぎていれば、下記の一般規則で即時通知される
  - **通知判定の一般規則**: 起動時・スリープ復帰時に限らず、**すべてのスナップショット更新時**に「通知時刻 ≤ 現在 < 開始時刻 かつ 未通知の通知回」を評価し、該当があれば即時通知する(同期遅延で通知時刻経過後に初めて取得された予定・寝ていた間に通知時刻を過ぎた予定の取りこぼし防止)
  - 開始時刻を過ぎた予定には通知しない(一覧の進行中表示で足りる)

## 永続化

カレンダーデータは **state.json に保存しない**(メモリ内のみ)。通知済み管理もプロセス内で持ち、再起動時は上記 catch-up 規則でやり直す。

## Core/Platform分離とテスト方針

既存の方針(純粋ロジックは `KokukokuCore`、AppKit/EventKit依存は `Kokukoku`)を維持する。

- **Core(ユニットテスト対象)**: CalendarEvent モデルと論理キー / Meet URL抽出 / 表示フィルタと安定ソート / 二層スナップショットの差分(変更照合・中止判定含む) / 間隔計算と強調判定 / 通知タイミング計算・通知済み管理・catch-up判定 / 予定セクションの描画要素構築とパネル高計算(PanelElementsBuilder・PanelLayout拡張)/ 設定のparse・validate
- **Platform**: EKEventStore アダプタ(権限・購読・クエリ・EKEvent→CalendarEvent変換・start/stopライフサイクル)/ 通知パネルの表示制御 / ブラウザでのURLオープン / スリープ復帰等のシステムイベント購読
- EKEvent→CalendarEvent 変換は EKEvent への依存を薄いプロトコルで切り、変換ロジック自体をテスト可能にする
